# How serial tracking works

This is the plain-language guide to serial-number tracking. Read it before you change anything under `migrations/021`–`034`, `src/serials.rs` or `src/serial_reconciliation.sql`. The [API contract](api.md#serial-command-admission) is the authoritative request reference; this page explains the design and how to change it safely.

## The one-sentence version

When a SKU is serial-controlled, every physical command must name each unit it touches, and the database refuses to commit unless the named units, their recorded history and the warehouse's stock all agree.

## Vocabulary

| Term | Meaning |
|---|---|
| **Serial-controlled SKU** | A product created with `serial_controlled: true`. The choice is made once per tenant/SKU, before any stock exists, and never changes. |
| **Label** / **serial** | The literal, case-sensitive ID printed on a unit (`Unit-A` and `unit-a` are different units). Never trimmed, normalized or generated by the server. |
| **Unit** | One physical item: tenant + SKU + serial, with a fixed lot. |
| **Place** | Where a unit is right now: `on_hand` in a bin, `staged` for an order line (optionally in a package), `shipped`, `in_transit`, `lost` or `missing`. Stored as JSON. |
| **Step** | One immutable change of a unit's place, caused by one event. Steps form a chain per unit (revision 1, 2, 3, …). |
| **Observation** | The exact list of labels an operator scanned for one target in one command, kept verbatim — including an explicit empty list for a witnessed zero count. |
| **Head** / **batch** | A per-tenant/SKU version counter. Every event that touches a controlled SKU creates a new batch (version) for that SKU. Reads and writes use it to detect that someone else changed the same SKU. |
| **Target** | Which part of a command a label group belongs to: `[]` for a single quantity, `[line_id]` for a return/dispatch line, `[order_line, bin, lot]` for a package line. |

## Data model

All tables are created in `migrations/021_serial_tracking.sql` and are append-only or tightly guarded.

```
wms_serial_modes          one row per tenant/SKU: controlled or not (immutable)
  └─ wms_serial_heads     current version of that SKU's identity history
       └─ wms_serial_batches   one row per (SKU, version) → the event that made it
            ├─ wms_serial_steps        per-unit place changes in that event (immutable)
            └─ wms_serial_observations exact scanned label lists in that event (immutable)
wms_serial_units          current place of each unit = projection of its latest step
```

Only two tables change in place. `wms_serial_heads` advances its version with each batch. `wms_serial_units` is a *projection*: its `place` and `revision` must equal the unit's latest step. Modes, batches, steps and observations are history that cannot be changed or deleted.

## Write path: how a command commits

1. The client sends the normal physical command plus `serial_inputs`: one `{target, sku, serials}` group per target.
2. `src/serials.rs` validates the input shape and quantities against the command (`validate_inputs`, `validate_context`), then plans each unit's before/after place.
3. In **one transaction** the server writes stock, movements, the event, the command receipt, the outbox row, *and* the new batch, steps, observations and unit projections.
4. At commit, **deferred constraint triggers** re-check everything that changed against the final transaction snapshot: labels match targets exactly once, quantities equal label counts, steps chain correctly, and serial custody equals stock (units on hand in a bin = stock in that bin, staged units = allocations, and so on). Any mismatch rolls the whole command back.

Migration 032 makes step 4 cheaper without weakening it: a trigger only *queues a key* ("this event/SKU/warehouse needs checking"), and each key is checked once at commit. Ordinary SQL cannot insert or delete those keys.

Recovery uses the same journal as every other command: retrying the exact original request (same request ID, actor, facility and `serial_inputs`) returns the original result.

## Read path: full reconciliation

`GET /v1/warehouses/{id}/reconciliation` returns a `serials` section built by **one** read-only, repeatable-read SQL statement, `src/serial_reconciliation.sql`, under the normal 10-second statement timeout. It answers two questions:

- **`source_ok`** — Is every recorded fact backed by its original event? Each event's original command, inputs, heads, batches, steps and observations are re-validated from scratch. Each unit projection must equal its latest step.
- **`physical_ok`** — Do the custody equations hold for this warehouse? Serial units in each place must match stock, allocations, packages and transfers.

`ok` is `source_ok AND physical_ok`, and it feeds the warehouse's overall reconciliation `ok`.

### Why the statement looks the way it does

The validity rules were first written as per-row PL/pgSQL functions in migration 021. They are correct but slow at scale: the full check called them tens of thousands of times. Since then, each change has kept **exactly the same verdicts** and done the work in fewer, larger passes:

- Each event, step list and observation is expanded **once** into a materialized CTE, then joined. CTEs are not indexed, so the statement uses hash joins and `GROUP BY` aggregates instead of correlated lookups into a CTE.
- "Unit's place at version *v*" uses `DISTINCT ON (serial) … ORDER BY revision DESC` over steps, which matches `wms_serial_at_version` without calling it per label.
- Input validation resolves each distinct command's targets once (`wms_serial_command_targets`, migration 034), then checks every input group in set form.
- Guards such as `CASE WHEN jsonb_typeof(x)='array' THEN … END` keep malformed stored JSON out of array functions, so damaged data produces `false`, not an error.

On the retained 16,000-label scale fixture this takes about 4 seconds; the per-row form took 39–54 seconds on the same database. See [performance](performance.md).

## Migration map (021–034)

Migrations are append-only: an applied migration's SHA-256 is recorded and any change to it is rejected at startup. Each later migration adds a faster equivalent next to the original; none relaxes a rule.

| Migration | What it adds |
|---|---|
| 021 | Tables, immutability triggers, the original validators and the deferred commit proofs. |
| 022 | Fixes helper lookup during `pg_restore` (empty `search_path`). |
| 023 | Resolves a command's targets once per validation call. |
| 024 | Decodes each original event payload once per check. |
| 025 | Read-only event validation that accepts pre-resolved command targets. |
| 026 | Index for per-event batch lookups. |
| 027 | Checks each distinct (SKU, lot, place) reference once. |
| 028 | Byte-exact (`"C"`) collation for historical lookups. |
| 029 | Statement-local source sets for scoped custody checks. |
| 030 | Reuses those sets for stock, staging and package custody counts. |
| 031 | Fast path for printable-ASCII labels; full Unicode rules still apply to everything else. |
| 032 | Deferred-check keys: each changed key is checked once at commit. |
| 033 | Direct target dispatch for ordinary counts and moves. |
| 034 | One target resolution per command for set-form reconciliation. |

## Changing serial code safely

1. **Never edit an applied migration.** Add a new numbered migration and register it in `src/persistence.rs`. Update the migration count in `tests/serial_admission/restore.rs` and the schema helper in `tests/serial_registry.rs`.
2. **Prove it gives the same answers.** For a rewrite of an existing check, add a differential test that compares the new result with the original function or the frozen predecessor (`tests/fixtures/serial_reconciliation_v24.sql`), on clean data *and* on deliberately damaged rows. `tests/serial_admission/resolved_sources.rs` is the template: it disables immutability triggers inside a rollback-only transaction, corrupts one thing at a time, and compares every verdict.
3. **Make sure the test can fail.** Temporarily remove one predicate from your new code; at least one case must fail.
4. **Check scale.** Run the ignored scale tests:
   ```bash
   # Starts a disposable socket-only PostgreSQL and sets WMS_TEST_DATABASE_URL.
   bash scripts/local-postgres.sh cargo test --locked --test serial_scale -- --ignored --nocapture --test-threads=1
   ```
5. **Keep the timeout.** Do not raise the 10-second statement timeout to make a query pass.
