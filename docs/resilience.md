# Sustained HTTP and crash recovery qualification

`scripts/resilience-rehearsal.sh` exercises the production image through actual HTTP against two independent API processes sharing one disposable PostgreSQL primary. It uses real mode, one administrator, four distinct operator identities by default, and a second isolated tenant. The rehearsal never uses production connection strings or configured native/webhook receivers.

Run it against an immutable image ID from the production container build:

```bash
WMS_RESILIENCE_IMAGE=sha256:<64-character-image-id> \
  bash scripts/resilience-rehearsal.sh
```

Python 3, Docker, and an already built image are required. Set `WMS_RESILIENCE_ARTIFACT_DIR` to an empty directory to choose where raw evidence is retained. The script rejects mutable application image tags.

After recovery and before timed traffic, the probe saves one validated synthetic operational snapshot as private `snapshot-fixture.json`. The report binds its SHA256, byte size and warehouse version. This additional read is outside the sustained interval and its read/latency counts. The fixture permits exact response comparisons without rerunning a competing load generator; publish the sanitized report rather than the raw run directory.

| Variable | Default | Accepted range / meaning |
|---|---:|---|
| `WMS_RESILIENCE_SECONDS` | 60 | 60–3600 seconds of sustained traffic, excluding seeding and crash phases |
| `WMS_RESILIENCE_CLIENTS` | 4 | 2–16 distinct authenticated operator identities |
| `WMS_RESILIENCE_PRODUCTS` | 100 | At least client count, at most 2000 operational products; one extra product isolates recovery evidence |
| `WMS_RESILIENCE_OPEN_ORDERS` | 100 | 0–5000 open single-line orders; alternating orders are allocated |
| `WMS_RESILIENCE_LOTS` | 2 | 1–10 opening lot balances per operational product |
| `WMS_RESILIENCE_BINS` | 20 | 2–1000 storage bins |
| `WMS_RESILIENCE_REVIEW_MODE` | `resources` | Exact resource reviews with zero spurious conflicts; `warehouse` retains strict global-version fencing |
| `WMS_RESILIENCE_TRAFFIC_MODEL` | `independent-operators` | Each operator has its own reviewed snapshot and post-save full refresh; `shared-snapshot` preserves the earlier synchronized-round protocol |
| `WMS_RESILIENCE_SERIAL_UNITS` | 0 | 0 keeps untracked stock; 2–256 collects literal identities for every operational SKU/lot, requires independent operators and enough units for seeded allocations |
| `WMS_KEEP_QUALIFICATION_RESOURCES` | 0 | 1 stops owned containers and retains their database volume/network plus private disposition and final-state evidence |
| `WMS_RESILIENCE_POSTGRES_IMAGE` | `postgres:16-alpine` | Actual immutable database image ID and version are recorded |

Each untracked opening bin/lot contains 100,000 disclosed synthetic each units. Serial mode uses the configured number of original literal identities instead. Catalog creation, counts, orders and allocations all use actual authenticated HTTP commands, with setup duration reported separately. The default seeds 200 opening balances and 100 active orders. To qualify the larger operational profile used by the Store workload, set products to 500, orders to 500, bins to 100 and lots to 2: this creates 1,000 opening balances, 250 allocated orders and 250 pending orders before any timed traffic. The additional recovery SKU stays untracked and has its own two-line receipt, complete five-unit shipment and three-unit outstanding allocation. The harness verifies these active orders remain present and unchanged throughout the rehearsal. Serial clients move one fixed literal identity each and review its current source after every save; the remaining identities stay in place. This does not measure arbitrary-label contention or large complete counts. The final independent proof reconstructs all literal custody revisions, original steps/observations and global SKU heads from original events.

The run creates a uniquely labeled private Docker network, one uniquely labeled named data volume, and three uniquely labeled containers. API host ports are random loopback ports. API containers use UID 10001, read-only root filesystems, all capabilities dropped, and no new privileges. The PostgreSQL named volume deliberately persists across its container crash/restart. Cleanup verifies ownership labels before removing only this run's resources; it does not prune Docker resources or touch external databases. Raw artifacts contain disposable generated API credentials and remain private; only the sanitized `resilience.json` report belongs in `docs/qualification/`.

The rehearsal checks these failure boundaries:

The blocked and lost-response commands below use the untracked recovery SKU. Serial mode preserves its complete seeded identity data across these failures and then exercises tracked traffic, but does not kill a pending serial write. Interrupted serial-command recovery remains a separate qualification requirement. Image reports retain aggregate latency distributions; the earlier native serial diagnostic additionally retains individual cycle timings.

1. A local discard proxy sends a receiving command to the actual API, observes its successful commit, and deliberately closes the caller connection without sending the success response. The caller retries the exact original envelope through the other API. The original result is replayed, the seven-unit receipt line remains seven, and another line with the same SKU remains untouched.
2. A dedicated PostgreSQL session holds the warehouse row lock. PostgreSQL's blocking PID graph must show the actual HTTP command waiting behind that session before the API receives SIGKILL. The other API remains ready. The killed request has no committed receipt, its original envelope commits once through the survivor, and the restarted API replays it. The client refreshes Docker's random port mapping after restart.
3. Another actual HTTP command waits behind the same database row-lock barrier. PostgreSQL receives SIGKILL while that transaction is pending. Both APIs must return readiness 503 while process liveness remains 200. PostgreSQL starts from the same named volume and reports unclean-shutdown recovery. Every WMS table's sorted-row SHA256 and row count must match its pre-crash fingerprint before retrying the pending command. Both API pools recover without an API restart. The original command commits once and replays through the other replica.
4. For at least the configured sustained interval, each operator independently moves its own SKU between two bins. Each starts with its own full snapshot, submits a command from that captured review, validates its own full post-commit refresh, then replays the exact original envelope through the other replica. The refreshed version must include the committed result, and the operator's exact source/destination quantities must match its move parity. That refresh becomes the operator's next review. A slow operator does not impose a barrier on other operators. Every client must complete work; counts may differ between clients. Every snapshot checks operational reconciliation, the exact configured catalog SKU set and every seeded active order ID/state; retained completed history is permitted. A definite stale 409 permits a refreshed review and new request; an ordinary conflict, ambiguous failure, failed refresh or changed replay fails the run. Setup remains outside the timed phase.

Independent-operator action latency runs from command submission through the validated full post-save refresh, matching the dashboard's busy period. Initial review acquisition and deliberate exact replay are excluded from that action sample but included in elapsed throughput. Snapshot, write-attempt and replay distributions are retained separately. Each client has exactly one initial read, one post-commit read per successful move and one extra read per stale retry. Reports expose these per-actor counts and use `rounds: null`; independent loops have no common round count. Clients run continuously without human think time. Python opens an HTTP connection per request; the measurement excludes browser rendering and physical input.

For a comparable repeat of an earlier profile, explicitly set `WMS_RESILIENCE_TRAFFIC_MODEL=shared-snapshot`. That mode reads one full snapshot per synchronized round and excludes a post-save refresh from action latency. `WMS_RESILIENCE_REVIEW_MODE=warehouse` forces the earlier shared-version contention; the default resource mode requires zero spurious conflicts on disjoint SKU lanes. These traffic models measure different read volumes and latency scopes, so their throughput or p95 values must not be presented as a speedup comparison. Both include exact replays in elapsed throughput without counting them as physical moves. The protocol regressions exercise both models, independent progress despite a delayed client, original envelope/replica ownership, strict-version conflict refresh, and failure without replacement after a bad refresh/replay.

The final proof reads actual PostgreSQL rows independently of the application's reconciliation endpoint. It reconstructs every bin/lot's physical quantity from append-only movements, every reservation from allocation ownership, and received quantities from the exact receipt/line movement identity. It checks receive 18 minus ship 5 equals 13 recovery units in custody, three recovery units plus the seeded allocations reserved, all opening physical custody conserved, each operator bin's expected move parity, and every seeded order's exact pending/allocated status. It then checks one command receipt, event, activity entry and contiguous version for each successful request, original actor/result/command identity, exact OMS/TMS outbox ownership, zero unconfigured delivery attempts, tenant isolation and actor-bound replay rejection. Both replicas must also return successful full-ledger reconciliation.

Expected execution counts are derived from the configured fixture before comparing them to actual PostgreSQL rows. Setup commands equal `bins + 2 + products × (lots + 1) + open_orders + ceil(open_orders / 2)`: bins, the recovery product/receipt, operational product/count commands, orders and allocations. Recovery contributes exactly 13 committed commands. Each timed physical move contributes one further command; exact replays and definite rejections contribute none. Physical movement rows must equal `products × lots + 9 + committed_moves`: opening counts, two receipt lines, one putaway, two picks, two shipment allocation movements, two recovered crash moves and timed moves. Command/event/activity totals must match setup plus recovery plus timed work, with exactly two additional TMS outbox rows. The report includes both expected and observed counts and fails on any mismatch.

The report binds these results to the running immutable application image, that image's build-source fingerprint, all qualifier/helper script hashes, database image/version, and checked migration hashes. A change to a qualifier/helper script during execution fails the run. The complete release gate requires both untracked and serial profiles with the same image and exact migration chain; each remains a separate report. Local restart-to-readiness durations are observations for that run, not recovery SLOs. This is evidence for local process survival, transaction atomicity, request recovery and PostgreSQL crash durability. It does not qualify database failover, host loss, a production load balancer, deployed network latency, physical warehouse scanners, native receiver deployment, or facility throughput. No production throughput SLO is inferred from a synthetic fixture.
