# Implementation evidence

This page records what has been proven about StateSet Warehouse, how, and what hasn't been proven yet. The summary comes first; the dated runs below it are the full record, newest first, including every failed attempt.

## At a glance

**Proven in software** (synthetic data, local runs):

| Claim | Latest evidence |
|---|---|
| Every stock change, reservation, receipt and serial unit can be rebuilt from immutable history, and the database rejects commits that disagree | [0.3.0 gate](qualification/release-20261022-v0.3.0/verification.json): final reconciliation passes on both API replicas |
| Retrying a lost request returns the original result, never a second change | 0.3.0 gate: thousands of exact cross-replica replays per workload, zero mismatches |
| API and PostgreSQL crashes mid-write lose or duplicate nothing | 0.3.0 gate: every table fingerprint unchanged after each forced crash |
| A backup restores to an identical database | 0.3.0 gate: archive restore with every table fingerprint and migration digest matching |
| Full serial reconciliation stays inside its 10-second limit at 16,000 labels | 0.3.0 gate; the 16,000-label scale fixture takes about 4s, from 39–54s before |
| Serial saves meet a 1,000ms p95 with eight concurrent operators | [native profile after migration 035](performance/native-serial-sku-scope-035.json): 772ms (unreleased 0.3.1 work) |
| The public source and its history contain no unreviewed secrets, and dependencies are permissively licensed | [source audit](qualification/release-20261022-v0.3.0/source-audit-report.json) and [license review](qualification/release-20261022-v0.3.0/source-license-review.json) |

**Not yet proven:**

- Production deployment, deployed identity (WorkOS), native OMS/TMS and MCP clients.
- Real scanner hardware and a signed [physical facility acceptance](facility-acceptance.md).
- Managed database failover, cross-region availability and real-warehouse capacity. All measurements so far are synthetic, on a shared host.
- Hosted CI on GitHub (blocked by account billing).

**Reproduce:** run the complete gate with the [release profile](release-qualification.md#run-the-release-profile).

## Development terminal recovery concurrency — 2026-10-19

The [targeted verification](qualification/development-terminal-journal-20261019/verification.json) covers an unreleased recovery fix. Two processes could previously publish different stage filenames at the same journal sequence number, leaving a forked history. Checkpoints now claim one shared filename per sequence position with an exclusive hard link. A competing writer reopens the winner's history instead of adding a conflicting outcome. A payload checksum detects accidental changes to the final checkpoint, which has no later hash-chain entry.

All **17 terminal checks** pass, including a deterministic race, separate Node processes, byte-preserving continuation of legacy uncertain journals, detection of existing forks and final-checkpoint changes, plus actual PostgreSQL/API lost-success recovery, physical serial movement and PTY facility creation. A retained transport intent pins the Freight endpoint/tenant; every POST checks actual `/v1/access` tenant identity and `operations.write`. Changing authority cannot redirect the pending request, while a secret can rotate within its original tenant.

## Persistence and integration boundaries

Current stock, products, locations, receipt lines, orders and allocation ownership use normalized PostgreSQL rows. Database triggers independently enforce physical movement, reservation and exact receipt-line balances. Movement/activity histories are append-only and paginated. Operational reads include active work, bounded completed work and bounded recent history. The former 8 MiB warehouse JSON aggregate limit is removed; writes still serialize within a warehouse. State, archived details and order/receipt history reconstruct line/allocation children from normalized rows even if cached JSON child types are malformed. The [workload report](performance.md) retains baseline, intermediate and final active-work measurements; the prior larger Store profile passed on a fresh disposable PostgreSQL cluster.

The [native integration report](native-integrations.md) identifies the actual Sync and Freight routes, authentication, response envelopes and unresolved contract gaps. Sync remains the commercial order authority; WMS owns physical inventory; Freight creates and executes transportation plans. Source-derived contract tests do not establish deployed credentials or the two applications' tenant mappings.

Native OMS writeback defaults to held because the legacy upstream endpoint lacks conditional revision and terminal-state fences. An additive [companion receiver patch](../integrations/stateset-sync-server/README.md) supplies the atomic predicate, exact source-line proof and immutable success/rejection receipts. It is compiled and tested against actual upstream types but remains unapplied and undeployed in the sibling OMS. Opt-in WMS `conditional_v1` mode requires that deployed receiver and verified tenant capabilities; it never falls back to the legacy endpoint. Native Freight import creates a planned load; it does not establish carrier acceptance, pickup or delivery. Generic warehouse event webhooks remain a separate producer contract requiring compatible consumers.
