## Concrete acceptance results

- The concurrent last-stock test allows one allocation to reserve ten available units; competing attempts cannot oversell. An identical-request race records one command, event and delivery intent.
- Repeated SKU lines retain independent reservations and staged quantities. Returning one line's picked units cannot release another line's staged stock.
- A partial pick can be blocked by an exception, physically returned, released, recounted, resolved and allocated again. Returning packed units invalidates packing. Shipping still requires a complete repack and physical handoff evidence.
- A separate real-workspace scanner test receives exact same-SKU lines B=2/A=3, then picks B=1/B=2/A=2. A different authenticated actor counts the storage bin while labels are confirmed; stale confirmation is blocked until reload/rescan. The UI completes putaway, packing and handoff; exact canonical line quantities, zero residual stock and full historical reconciliation pass. No API interception is used; input is simulated keyboard-wedge input, not physical scanner hardware.
- The HTTP lifecycle receives 12 units across two same-SKU receipt lines, deduplicates a repeated receipt request, recovers a short pick, records a four-unit physical shortage, then ships eight. Final physical and reserved stock are both zero and independent reconciliation passes.
- Thirty thousand retained audit records exceed the former 8 MiB aggregate ceiling. Commands remain operable, the operational history view stays bounded, all original evidence remains stored and cursor pages expose older evidence without overlap.
- Completing 25 receipts keeps the oldest receipt accessible and its exact line evidence reconciled beyond the completed-work dashboard window.
- A failed final outbox write rolls back stock, movement ledger, event and saved command receipt. Reconnecting and retrying a committed request returns its original result without another physical movement.
- The independent SQL fixture receives ten units, reserves seven across two same-SKU order lines and picks two. Storage is eight on-hand/five reserved; staging is two on-hand/two reserved. Direct physical, reservation and receipt-evidence corruption is rejected, as are movement updates and audit deletion.
- Native adapter contracts reject fractional units, mismatched source identities, unsafe/partial/unknown fulfillment statuses, redirects and oversized responses. Freight import retries retain a stable prepared request. The OMS adapter never posts to the unsafe legacy fulfillment endpoint.
- Conditional OMS requests freeze a complete physical shipment, recipient, revision and remote request UUID. Simulating remote acceptance followed by HTTP 500, then source cancellation, still replays the same original request without a source refresh or second remote effect. A malformed acknowledgment retains uncertainty.
- A durable OMS rejection remains immutable after a separately reviewed replacement succeeds. A request with unknown acceptance cannot be replaced. Independent PostgreSQL sessions exercise the actual companion migration with deterministic lock-wait barriers for duplicate requests, payload conflicts, cancellation-before-fulfillment and fulfillment-before-cancellation races.
- An actual custom-format archive round-trip restores every WMS table into a fresh database with identical hashes, tenant scopes, warehouse versions and all six migration digests. Original receive/import replays do not alter evidence; rejected/uncertain native journals recover and a new post-restore count reconciles. See [the sanitized restore report](qualification/restore.json).
- Competing warehouses cannot import the same complete native OMS source, including an attempt through an ordinary native-prefix command. A retained transport intent pins the Freight endpoint/tenant; every POST checks actual `/v1/access` tenant identity and `operations.write`. Changing authority cannot redirect the pending request, while a secret can rotate within its original tenant.

## Persistence and integration boundaries

Current stock, products, locations, receipt lines, orders and allocation ownership use normalized PostgreSQL rows. Database triggers independently enforce physical movement, reservation and exact receipt-line balances. Movement/activity histories are append-only and paginated. Operational reads include active work, bounded completed work and bounded recent history. The former 8 MiB warehouse JSON aggregate limit is removed; writes still serialize within a warehouse. State, archived details and order/receipt history reconstruct line/allocation children from normalized rows even if cached JSON child types are malformed. The [workload report](performance.md) retains baseline, intermediate and final active-work measurements; the final large profile passed on a fresh disposable PostgreSQL cluster.

The [native integration report](native-integrations.md) identifies the actual Sync and Freight routes, authentication, response envelopes and unresolved contract gaps. Sync remains the commercial order authority; WMS owns physical inventory; Freight creates and executes transportation plans. Source-derived contract tests do not establish deployed credentials or the two applications' tenant mappings.

Native OMS writeback defaults to held because the legacy upstream endpoint lacks conditional revision and terminal-state fences. An additive [companion receiver patch](../integrations/stateset-sync-server/README.md) supplies the atomic predicate, exact source-line proof and immutable success/rejection receipts. It is compiled and tested against actual upstream types but remains unapplied and undeployed in the sibling OMS. Opt-in WMS `conditional_v1` mode requires that deployed receiver and verified tenant capabilities; it never falls back to the legacy endpoint. Native Freight import creates a planned load; it does not establish carrier acceptance, pickup or delivery. Generic warehouse event webhooks remain a separate producer contract requiring compatible consumers.
