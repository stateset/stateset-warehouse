# Changes

## 0.4.2 — 2026-10-28

- **Clients use background reconciliation runs.** The dashboard's movement ledger, the terminal's reconciliation view and `--once reconciliation` try the synchronous proof first; when it exceeds the 10-second request deadline (HTTP 503) they start a background run and poll it to completion. Two MCP tools, `wms_reconciliation_run_start` and `wms_reconciliation_run`, expose runs to agents.

## 0.4.1 — 2026-10-27

- **Background reconciliation runs** (migration 039). `POST /v1/warehouses/{id}/reconciliation/runs` starts the same complete proof as `GET .../reconciliation`, in one read-only snapshot, under a 120-second statement deadline instead of the 10-second request deadline; poll `GET .../reconciliation/runs/{run}` for its status and result. A warehouse whose serial history no longer reconciles within one request still gets its full proof. Runs left unfinished by a stopped API process read as failed after 10 minutes. The release gate's final reconciliation on both replicas now uses runs, with every HTTP request still bounded at 12 seconds and no 503s allowed.
- **Full reconciliation scales further with serial history.** The serial proof joined each event to its input class on the command alone and compared inputs afterwards, so identical moves were compared pairwise (89,700 rejected pairs for 300 identical moves). Each event now carries one exact class id. Reconciliation also runs without JIT compilation, which took 12–16 s past about 5,500 serial commands. On the same snapshot of 5,943 single-label moves the serial proof took 3.9 s instead of 9.9 s, with an identical verdict. Its cost still grows with history, about 0.65 ms per serial command.
- **Scanner code IDs.** The dashboard scanner panel also accepts a bin, SKU or lot label that arrives after a leading symbology identifier such as `]C0`. Matching stays exact and case-sensitive. Forms, serial fields and the terminal still record scans exactly as typed.
- Code structure, no behavior change: the order, receipt and help dialogs moved out of `App.tsx` (2,878 to 2,350 lines). `persistence.rs` is split into startup, load, save and command-execution modules (1,911 to 490 lines). The serial custody equations and tests moved out of `serials.rs` (1,963 to 837 lines).

## 0.4.0 — 2026-10-27

- **GS1 scanning.** `POST /scans/parse` turns a GS1-128, DataMatrix or QR scan into its exact GTIN, lot, expiry date and serial, with check digits, lengths and character sets verified and the GS1 century rule for dates. Unsupported or malformed data is refused, not partly parsed. A product is identified only through reviewed GTINs (migration 038): admin-managed, audited, normalized to GTIN-14 and unique per warehouse.
- **Bin capacity** (migration 038): optional per-bin limits in whole units and distinct SKUs, admin-managed and audited. Putaway skips full bins and splits stock across bins.
- **Startup refuses a database migrated by a newer release.** If the migration ledger contains a migration this binary doesn't know, startup stops before applying anything, naming the unknown migrations. An older release can therefore never run against a newer schema without that release's rules. Roll back by restoring the pre-upgrade backup instead.
- **Planning.** Every plan below reserves and moves nothing. Each task is the exact canonical command, with its reviewed versions, confirmed through the normal command journal.
  - Directed putaway: same lot, then same SKU, then a requested or SKU zone, then any empty bin. There is no capacity model.
  - Batch picking: up to 50 orders per walk, stops in natural bin order and one tote per order. Blocked orders and unavailable lots are reported, not planned.
  - Scheduled cycle counts: Pareto ABC classes by picked units, intervals of 7, 30 and 90 days, last-counted times from the original count events, blind by default.
  - Saved replenishment rules (migration 036): admin-only, audited and removed with their product or bin, plus a due-now work queue.
- **Labels.** 203 dpi ZPL labels for bins, products, 4×6 cartons and serial units. Code 128 barcodes encode exact values and reject what they can't carry; free text is escaped against ZPL injection.
- **Carrier labels** (migration 037) record the carrier, service, tracking number, exact decimal rate, observed carton and a ZPL or HTTPS label on an open package. A package has one active label; labels are immutable apart from one void, and can't be added after handoff or unpacking. The WMS never calls a carrier; the TMS or an operator supplies the label.
- Dashboard panels for each: putaway (Receiving), batch picking (Fulfillment), cycle counts, label printing and saved rules (Inventory), and carrier labels on each package. Ten new MCP tools.
- Integration tests run every planned task through the real command path against PostgreSQL. The restore rehearsal populates both new tables.

## 0.3.1 — 2026-10-27

**Highlights**

- **Faster serial saves.** Each save now checks serial custody only for the products it touches, not every serial unit in the warehouse. The native serial latency profile now meets its 1,000ms p95 target (772ms, from 1,242ms), and throughput more than doubled (18.8 moves/s, from 8.3).
- **Safer rollbacks.** Startup refuses a database migrated by a newer release, naming the migrations it doesn't know, before applying anything.
- **Behavior change.** Custody damage confined to one product, which only a database guard bypass can create, now blocks saves for that product only, not the whole warehouse. Full reconciliation still reports it.

**All changes**

- Check serial custody per (warehouse, SKU) at commit in append-only migration 035, instead of rescanning every serial unit in the warehouse on every save. Each custody equation and place reference involves one SKU. Every mutation that can change custody now queues its SKU: SKU-bearing rows, the old and new places of changed serial units, package closures and receipts through the SKUs that reference them, and transfer losses through their original line. Location changes keep the warehouse-wide check. A new differential test shows the per-SKU checks together give exactly the warehouse-wide verdict on clean data and on five kinds of deliberate damage. It fails if the per-SKU check is disabled. On the retained 16,000-label fixture (8 SKUs) the commit-time check takes 18–24ms against 100–192ms. The optimized native serial profile now passes its 1,000ms action-p95 limit at 772ms (1,242ms before), with 18.8 against 8.3 moves/s. **Behavior change:** custody damage confined to one SKU, which only a guard bypass can create, now blocks commits for that SKU only, not the whole warehouse; full reconciliation still reports it.

## 0.3.0 — 2026-10-22

**Highlights**

- **Warehouse terminal for the floor.** A keyboard- and scanner-first terminal client with an operations board, work queues, guided receiving, picking, packing, transfers, returns, quarantine and exception handling, readable reviews of every save, and safe recovery after lost connections. Ghostty/Kitty terminals also get visual views: flow, stock by bin, floor plans and barcodes.
- **Partial and package fulfillment you can finish.** Partly shipped orders stay visible, with an exact review of remaining work and the choice to continue picking, return staged stock or close the remainder.
- **Faster full serial reconciliation.** Checking every serial label in a warehouse is now done in a few large passes instead of one lookup per label. At 16,000 labels it takes about 4 seconds instead of 39–54 seconds, with identical results. This fixes the timeout that failed the 2026-10-21 release gate.
- **Cheaper serial saves and reads.** Repeated validation work is shared within each save and each read. Every original rule still applies (migrations 030–034).
- **Release tooling.** A runnable live-browser suite, storage and network preflight for the release gate, full-history source auditing and retained dependency license notices.

Known limits: the serial native latency profile still misses its 1,000ms p95 target (measured 1,242ms at 2,048 labels); the cause and a proposed fix are in [performance](docs/performance.md#known-serial-write-bottleneck--2026-10-22). Production deployment, scanner hardware and physical facility acceptance remain unqualified.
