# Ghostty WMS operations center

The StateSet Warehouse TUI is a keyboard-first operations center designed for Ghostty. It runs on Node.js 22.12+ on POSIX systems with no runtime npm dependencies. Local qualification uses Linux. It calls the canonical REST API and works with the same tenant, actor, roles, serial admission and immutable command receipts as the dashboard and MCP server.

```bash
export WMS_URL=https://warehouse.example.com
export WMS_TOKEN_FILE=/secure/path/operator-token
bash scripts/warehouse-tui.sh
# Read-only automation:
bash scripts/warehouse-tui.sh --warehouse wh-main --once inventory
```

The repository launcher uses a compatible Node on `PATH` or in a local nvm/fnm installation. Set `WMS_TUI_NODE` to an explicit executable when needed. It validates the runtime before starting the console.

Use an existing deployment with an individual operator credential. `WMS_TOKEN` is also supported; do not put bearer tokens in command arguments. Remote origins require HTTPS. Loopback HTTP is allowed for local development. Authentication redirects are refused. WorkOS users can supply a valid access token; this client does not implement browser sign-in or automatic token refresh. Update an expired credential and reopen the same recovery scope.

The numbered terminal menus provide facility selection, inventory/products/bins, receiving and returns, orders and shipment review, serial custody/history, lots, transfers, exceptions, retained history, reconciliation, operations and iCommerce interoperability. Typed forms cover physical workflows and administration. Inputs use whole each units. Multi-line work collects exact original line identities. Serial forms require actual literal scans; custody reads never prefill observed labels. A complete zero count needs explicit confirmation. Partial shipments, transfer dispatch and returns preserve their original target groups.

## Navigation and views

Use Ghostty or another ANSI terminal. The interactive client uses a separate full-screen buffer, restores the shell buffer and input mode on exit, and follows the terminal's colour palette. `NO_COLOR=1` disables colours while retaining keyboard navigation and text status labels. It does not modify your terminal profile. Resize a pane to reflow its menu or table.

Resizing retains unfinished menu searches, table searches and numbered choices, including the editing cursor and literal Unicode text. Enter still submits the choice; Esc discards that view's unfinished input. Selected rows stay visible. Unselected tables keep the previously visible record in view, including after resizing a detail view. Long reviews retain the same source passage when lines reflow. These adjustments stay in memory and do not refresh data, record work or change original requests.

The operations board shows allocation, picking, packing and shipping stages, incoming receipts, priority work, quality holds and original-request recovery. A compact pane retains task counts, a UTC snapshot time and a command bar; larger panes show the complete scope and grouped navigation. While the home board is idle, read-only refresh runs every 15 seconds. `r` refreshes immediately and `z` pauses/resumes automatic reads. The board shows snapshot age and an explicit stale warning after failed reads or when retained data becomes old. Refresh pauses while a menu entry is unfinished and stops inside task, inspection and request-review views. `t` opens work queues, `i` stock, `o` orders and `w` observed work. `v` opens the complete context when a compact screen shortens it. Pending recovery and read failures remain visible. Menu numbers are stable across searching and paging.

The renderer is checked at 49×20, 70×24, 70×44 and 120×32, with additional smaller-pane checks. Real pseudoterminal acceptance includes 49×20 Ghostty-style input and 70×44 operational workflows. These are software terminal checks; they do not establish physical scanner, Ghostty GPU/compositor or facility acceptance. No font, theme, shell profile or Ghostty configuration is changed.

The development client opens a compact overview with facility, operator, tenant, synthetic-demo status, on-hand/reserved each units, open orders, incoming receipts, open exceptions and pending original requests across your facilities. Counts describe the displayed operational snapshot, not all retained history. On-hand minus reserved is not a sellable-availability calculation: lot holds, expiry and other policies still apply. The timestamp and age show when the snapshot was read; `r` refreshes it immediately. Automatic reads verify the same live operator and tenant first. A session failure stops automatic reads and retains the old data with a hold; `r` retries verification, and `c` can inspect original requests locally while held. Writes always fetch their own fresh review before collecting work.

Move through menus with ↑/↓ or Tab/Shift-Tab and press Enter to open the highlighted action. Home/End select the first/last action; PgUp/PgDn or ←/→ change pages. Type a shortcut and press Enter: `t` work queues, `i` inventory, `o` orders, `w` record observed work, `c` recovery, `r` refresh. Existing menu numbers are unchanged. `/text` searches menu labels, `/` clears the search, `n`/`p` page long menus, F1 or `?` opens a paged keyboard guide, and Esc or `q` returns or exits.

Inventory, products, bins, orders, receipts, exceptions, movements and activity use tables sized to the current terminal. F3 or `f` selects a filter; F4 or `s` selects sorting. `/text` searches within the active filter without case sensitivity; replacing a search starts from that filter's complete snapshot. `/` clears only the search; select **All records** to clear the filter. `n`/`p` or paging keys page, `r` reloads the snapshot, and a displayed row number opens its complete original fields in a paged detail view. Arrow keys highlight a row with a visible `›` marker, including with `NO_COLOR`; Enter opens its details. Enter returns when no row is selected; Esc always returns. `j` shows the current page as JSON. Refresh and returning from actions retain the filter, sort and search. Changing the view or refreshing clears the highlighted row so an action requires selecting again. Tables shorten long values with an ellipsis; use row details for exact IDs and literal labels. Compact stock tables reserve space for exact on-hand and reserved each quantities before allocating identity-column widths. Extremely wide quantities use multiple lines. Compact lot rows show the server availability verdict and physical/reserved/usable each figures, including zero. Numeric values are never abbreviated; full literal identities remain available in row details. Detail, serial/history, reconciliation and interoperability views also page their complete contents. These navigation and inspection actions are read-only.

Home work-lane shortcuts open fresh queue views directly: `a` allocation, `k` picking, `f` packing, `g` shipping, `d` inbound receiving, `b` receiving-bin putaway, `e` open issues, `u` high/urgent orders and `l` active partial/package fulfillment. Existing menu numbers stay unchanged. Wider boards show open issues and priority orders with age calculated from their original creation timestamps. These are attention cues, not invented SLA deadlines or proof that work is admissible.

Set `WMS_TUI_REFRESH_SECONDS` to a whole number from 5 to 300 to choose the home read interval. `0` starts paused; `z` then resumes at the default 15 seconds. Reads run sequentially, with no background refresh surviving departure from home. A failed snapshot read retains its original version and read time, shows unknown lane counts, and can retry at the next interval. A failed session check requires an explicit retry. Paused or unfinished-input snapshots become visibly stale as they age. Automatic reads never record physical work, retry a command or append recovery checkpoints.

Open **Work queues** with `t` or menu 20 for open orders by urgency, pending allocation, allocated/picking, picked, packed, high/urgent orders, incoming receipts, stock in receiving bins, open exceptions and active partial/package fulfillment. The original nine queue numbers remain stable; partial/package work is queue 10. Counts use the displayed operational snapshot; unavailable counts show `?`. Opening a queue reads a fresh snapshot. The receiving-stock queue uses configured receiving-bin types and positive on-hand stock, including reserved units. Queue membership does not establish sellable availability or authorize a movement; selected actions retain their role, identity and version checks.

**Lots and holds** (menu 9) and **Facility transfers** (menu 10) use tables with server batches of up to 100 records. `n`/`p` and paging keys cross batch boundaries after the last/first displayed page. Each screen identifies the batch and whether more records remain on the server. Search, filters and sorting apply only to that batch; an empty result can still advance to another batch. `r` returns to the first batch, retaining search/filter/sort. Previous batches are read again, so batches can show different warehouse versions. A failed page read keeps the displayed batch and cursor position for retry.

Lot tables show the server's availability verdict and physical, reserved and usable quantities; narrow panes retain identity and availability first. Availability filters use that verdict, including quarantine and expiry; the TUI does not calculate sellable stock from physical minus reserved. The database check time is displayed because expiry can change without committed warehouse work. Transfer tables include open **and settled** transfers, with inbound/outbound filters for the selected facility and a source-check status. Open row details for complete original lot controls, transfer identities and lines. Browsing does not record a physical observation.

Highlight a lot and enter `a` to quarantine it, record its original expiry, or perform the lot actions allowed by your role. Before collecting work, the client checks the selected version and exact SKU/lot against fresh canonical stock and lot-control evidence. Enter the actual reason and any expiry time; these values are never taken from the displayed row. Expiry entry requires an exact RFC3339 timestamp with an offset and up to six fractional digits, such as `2027-01-31T16:30:00.123456-08:00`. Invalid calendar dates retry locally. The original request retains the literal timestamp. Administrators can correct an already recorded expiry, or clear it with an empty correction field.

To release quarantine, an administrator must select the exact original hold and enter its disposition reason. Releasing one hold preserves any others. Releasing all holds does not override expiry or product expiry policy: use the refreshed server availability verdict. Lot actions retain the original-request review and explicit confirmation, affect the selected facility only, and do not move physical stock, reservations or serial custody. Returning from an action preserves the current batch and filter/search/sort.

At the destination facility, highlight an inbound transfer and enter `a` to receive an actual arrival. Select its exact original line from those with in-transit units, then enter the observed quantity, receiving bin and arrival reference. Serial-controlled goods require actual scans. Only the transfer and line IDs carry into the form. Before collecting work, the client re-reads the selected transfer at its original server position and checks the selected destination version, original identity, source verdict and current role. Changed versions or source evidence hold the action. Review the complete original request and explicitly confirm before submission. The source facility and settled transfers offer inspection only. Returning from an action re-reads the same batch and clears the highlight while retaining search/filter/sort. Transfer-loss settlement remains a separate administrator workflow.

Highlight a stock, order, receipt or exception row and enter `a` to open its actions. The first action reviews the complete original record; orders also show shipments and return eligibility. Other actions follow the signed-in role and the selected record's state. Stock supports moving and administrator counts; orders offer relevant allocation, picking, packing, handoff or cancellation forms; incoming receipts support receiving and cancellation. These suggestions are not server admission or availability proofs.

Order actions also let operators report an exception against the exact selected order, including completed orders. Enter the observed category and details; the client carries only the original order ID. From **Exceptions** or the **Open exceptions** queue, use row actions to review the full issue, inspect its linked order and shipments, or resolve an open issue. An order without a returnable physical handoff remains readable: its return-eligibility section shows the server's unavailable verdict and reason. Authentication and service failures still hold the review. Enter the actual resolution and review the complete request before confirming. Resolution carries only the original exception ID and rechecks the current role, facility and selected version. A resolved issue leaves the open queue; it remains in the full exceptions table. Reporting/resolving an issue does not change stock, reservations or original order fulfillment. OMS credentials do not gain exception-writing privileges.

Selected work carries only the explicitly chosen source identities, preserving exact case. Receiving and picking ask you to select the original line. Quantities, receiving/destination bins, reasons, carrier references and actual serial observations remain explicit inputs. Receive into an actual receiving dock, then use its stock row for putaway. Before collecting work, the client rechecks identity, facility, source record and the selected snapshot version. A changed version holds the action and requires refreshing the table; it never silently replaces an original request. Pending original work still blocks new writes across your facilities. Returning from an action reloads the table and clears its row selection while retaining the search. Esc from a selected-row form returns to that table, preserving its view context.

From a stock row, **Dispatch a facility transfer** carries the selected stock tuple into the first line and asks you to select a different destination facility from the server directory. Enter the actual reference, carrier handoff, original transfer-line ID and quantity. Additional lines select explicit original stock sources; the displayed remaining quantity is a limit, not an observation or admission proof.

The **Partial/package** lane (`l`) includes open package-mode orders before and after their first handoff, including backordered work. It excludes shipped, cancelled and closed-partial orders. It overlaps the status-based stage queues: it is the place to review mixed allocation, picking, packing and handoff work that a single header status cannot describe.

From an order row, **Review remaining fulfillment work** binds a fresh authenticated identity, selected facility/version, original order and verified package source. It shows exact each quantities per original line and in total: ordered, handed off, cancelled, unallocated, still to pick and picked/unshipped. Same-SKU lines stay separate, released reservations are excluded, and arithmetic remains exact beyond a single safe-integer aggregate. Picked/unshipped units may already belong to an open package; the review lists those originals and makes no availability claim. `j` opens the complete original review data.

Partial-order actions follow those original counters: allocate additional available stock, pick remaining exact lines, release unpicked reservations, return observed staged goods, or close the whole unshipped remainder once staged goods have been recovered. Picking/returning offer only original lines with remaining work; locations, lots, quantities and reasons remain explicit. The server still checks current package ownership and restrictions. Remainder closure requires a new explicit reason, complete request review and `yes`; declining creates no journal. It preserves physical handoffs and moves no goods. Closed/cancelled demand is shown separately and does not reappear as active work.

From an order with picked stock, **Pack a partial shipment** selects the exact original line/bin/lot tuple. Existing open packages and lines already entered in this draft reduce the remaining quantity offered. Enter the actual package reference and quantity. **Shipment packages and handoffs** opens the order's original packages; select a still-open package to unpack it or record its actual carrier handoff. Package and original-order IDs are checked against a fresh server review and the selected version before collecting work.

Orders with an original physical handoff offer **Authorize a customer return**. Choose the exact shipped order-line/lot from the server's current return eligibility, then enter a new return-line ID and the actual authorization quantity. Existing authorizations and draft lines reduce the offered remainder. Authorization alone moves no goods and implies no refund; an actual arrival still uses receiving.

Observed-work forms have a dedicated screen. Backspace, Delete, arrows and Home/End edit the literal field without changing its case or silently trimming spaces. Validation explains what to correct. Fast scanner input remains queued across prompts, with CRLF treated as one submission. Bracketed paste accepts one field at a time; multi-line paste is ignored. Esc cancels a form or request review before submission. Work reviews show readable scope, source IDs, each quantities, reasons and actual observations; `j` opens the complete original JSON without editing it. Outcomes show the committed or unresolved status with original data available through `j`. Page the review, press Enter to advance to confirmation, then explicitly type `yes` to record it. Esc after transmission cannot undo the physical record; original-request recovery remains authoritative.

At an each-quantity or complete-count field, enter `pack` to scan an actual packaging code. The client reads that exact SKU/code definition at the reviewed warehouse version, verifies its original-source verdict, and asks for the observed whole pack count. It converts with exact integer arithmetic, rejects totals over 1,000,000 each, and carries the original definition ID, factor, count and target in `unit_inputs`. `EA` returns to each entry. Disabled, changed or unverified definitions cannot authorize a conversion. Serial-controlled stock still requires one actual serial observation per each unit. The durable original request retains both the conversion evidence and each quantity; recovery never substitutes a newer definition.

Serial capture shows progress, target group, physical bin/move context and recent accepted labels. A malformed or duplicate scan explains the problem and repeats that slot, retaining earlier observations. Case remains significant; duplicate checks use the exact SKU and label. At an empty scan field, F2 undoes the previous observation, including across target groups. The final **unsent** request review also supports F2 to correct its last observation without rescanning the complete set. Empty targets require physical zero confirmation again if undone. Strings such as `undo`, `/undo` and `F2` remain literal labels; the function key is the correction control. Corrections retain the reviewed warehouse version. Once confirmed for submission, the durable original body and its recovery history cannot be edited through this workflow.

Forms capture a warehouse version before collecting work and retain it through submission. Creating a facility generates a new facility identity at version zero; a successful creation selects that facility. Concurrent facility work can cause a safe conflict; review again only after the previous original request is definitively resolved. Replenishment planning and native OMS/TMS writeback remain available through the dashboard/API/MCP.

## Graphics and visual operations

Press `m` at home or open menu 21, **Visual operations / labels**. Choose operations flow, stock by bin, configured floor plan, or a product photo/barcode preview. These views preserve exact text quantities, original case-sensitive SKUs, snapshot versions and capture times. `r` explicitly reads a fresh review; failed reads retain the previous snapshot marked **STALE**. Resizing, plan navigation and help send no warehouse commands.

`WMS_TUI_GRAPHICS=auto` (default) queries the terminal before sending images. Ghostty supports the [Kitty graphics protocol](https://sw.kovidgoyal.net/kitty/graphics-protocol/). Unsupported terminals, noninteractive output, `TERM=dumb`, `NO_COLOR`, and multiplexers use text in automatic mode. Set `off` to disable graphics explicitly; `kitty` attempts a capability query even with `NO_COLOR` or a multiplexer. It still requires a successful reply. Multiplexer passthrough must be configured separately. The client never changes Ghostty or multiplexer configuration. Headless `--once console` emits JSON only.

Graphics appear in panes at least 60 columns by 24 rows. Complete text pages remain available in smaller panes. Flow bars compare order-stage counts; stock bars compare the current bin page's physical/reserved each quantities, **not bin capacity or sellable availability**. Plan positions must be configured by the facility administrator. Missing plans/photos remain explicitly unavailable.

Within a visual board: `f` flow, `b` stock, `m` plan, `s` exact SKU, `r` refresh, `j` evidence, `n`/`p` pages and `q`/Esc back. Plans support arrow-key pan, `+`/`-` zoom, `/EXACT-BIN` find and `0` fit. Product previews use `l` label, `p` photo, `n`/`b` text pages. F1 or `?` opens help. The Code 128 preview encodes the exact SKU when it has 1–80 printable ASCII characters; unsupported values retain their original text. A product SKU label is not a captured serial observation or a shipping/carrier label. Screen previews do not print labels or establish physical scanner/printer acceptance.

The server supplies authenticated, versioned metadata and bounded PNG bytes; the client supplies bounded raster rendering and terminal escape sequences. Images travel as direct bytes, so SSH needs no terminal access to server paths. Only this client's image IDs are removed. Terminal replies are filtered before scanner input; malformed replies reject the interrupted field and require a complete rescan. See [server configuration and API](../docs/visual-console.md).

## Recovery

If the service is unavailable at startup or a later session check fails, the console stays open on **Connection held**. Press `r` to retry or `q` to exit safely; retries never send work. After an identity has been verified in this process, `c` can inspect that operator's saved original requests locally during the outage. Local inspection does not look up receipts, resend requests or append recovery checkpoints. A changed actor or tenant stays held: restore the original credential or exit and restart for the new identity. A successful retry checks the current role again.

Failed table refreshes, batch reads or selected-row actions retain the current data and search/filter/sort context. A **STALE** warning remains visible, and work actions wait for a successful fresh read. `v` shows the last successful read time and full failure reason; original row details and page JSON remain available for inspection. Retry with `r`, then select the intended row again. Returning to the home screen refreshes the authenticated session and overview. Nothing is retried or submitted automatically.

Before sending any physical command, the TUI writes its complete original JSON body and server/tenant/actor/facility scope into private recovery storage. It then fsyncs an immutable send-intent checkpoint. Files use 0600 and directories 0700, with exclusive publication, directory fsync and hash-linked history. Files contain operational request data, not bearer credentials. Default storage is `$XDG_STATE_HOME/stateset-warehouse` or `~/.local/state/stateset-warehouse`; set `WMS_TUI_STATE_DIR` or `--state-dir` for an explicit private directory. Storage must support local atomic hard links and fsync. Symlink recovery paths are rejected.

The development client uses schema 2 journals with one exclusive checkpoint filename per sequence position. Competing processes cannot publish different outcomes at the same position; the losing process must reopen the journal. Each checkpoint includes a payload checksum as well as the preceding file's hash, so an accidental change to the final outcome also holds recovery. These checks do not authenticate files against a malicious local owner.

Close older TUI processes before upgrading. The new client reads schema 1 journals from 0.2.0 and continues them with exclusive checkpoints, preserving all old files and the exact original HTTP body. Older clients cannot read the new format. Existing broken or forked histories remain held; the client never chooses an outcome or deletes evidence to repair them automatically.

A timeout, EOF, interrupted process, generic conflict, validation error or missing receipt retains the original request. Recovery shows the signed-in actor's work across facilities on the same server and tenant, including a newly created facility whose response was lost before it appeared in the directory. It can look up the actor-owned receipt at the original facility or resend the **exact original bytes**, with the original UUID, reviewed version, quantities, identities and serial observations. It never refreshes or replaces a pending request. A fully bound server proof can establish that a stale request never committed. Only completed work or that definitive rejection resolves a journal; unresolved work blocks new writes by that actor across facilities in the same recovery directory to prevent accidental duplicate physical recording.

Changing credentials to another actor, tenant or origin does not transfer pending work. Return to the original scope. Keep the recovery directory backed up privately; do not edit, delete, export publicly or fabricate receipts to bypass a hold. A disk error before a send checkpoint prevents transmission. A disk error after a response retains the original request for later receipt lookup/replay. The hash chain detects accidental modification; it is not a signature against a malicious local account owner.

`q` exits menus; Ctrl-C or EOF exits safely. Noninteractive use requires `--once`. Supported views are `session`, `warehouses`, `inventory`, `orders`, `receipts`, `reconciliation`, `recovery` and `console`. JSON output is read-only and may contain operational data. No headless write or automatic physical action is enabled.

## Check

```bash
npm --prefix cli test
# Full software acceptance: requires an isolated test DB and a built local API.
WMS_TEST_DATABASE_URL=postgresql://.../warehouse_test npm --prefix cli run test:acceptance
```

The suite exercises original-request recovery, exact source/version/role checks, raw input, scanner bursts, layout bounds, readable/original reviews, server paging, pack conversions, resizing, automatic board reads, exact partial fulfillment progress and operational workflows. `test:acceptance` fails if the isolated database or local API binary is missing. It includes real PostgreSQL/API and terminal actions for receiving, putaway, sorted queues, 101 lots, original-hold release, exception resolution, serial transfer receiving, observed pack conversion, guided dispatch, partial package handoff and an original shipped-line return. An owned pseudoterminal changes size during unfinished menu/table searches and verifies read-only navigation without new requests. A read-only fault proxy checks timed board refresh, stale-read retention, automatic recovery, pause during unfinished input, and absence of automatic reads in task views. Ordinary `npm test` skips the live test when `WMS_TEST_DATABASE_URL` is absent. See the root [verification instructions](https://github.com/stateset/stateset-warehouse#verify).

## Ghostty operator acceptance

Before using this console for facility work, record the exact console build, Node/Ghostty versions, pane sizes, font/scale and scanner model with its configured Enter suffix. In a controlled area, have an operator perform receiving, putaway, picking, partial packing, handoff, a return and uncertain-request recovery while an independent controller witnesses the actual stock and original records. Record task times and errors against targets chosen before the run.

Include capability detection, text fallback, photo/plan review, label readability and independent scan decoding at deployed font sizes, pane resizing during an unfinished search and scan, exact-case labels, duplicate/malformed scans, quantity visibility at the smallest deployed pane size, loss of service after submission, changed credentials, paused/stale board behavior and full terminal restoration on exit. Retain failures and original recovery files. These observations supplement the [signed facility acceptance process](../docs/facility-acceptance.md); the local synthetic terminal suite does not supply them or extend its machine-validated schema.
